# 2분 데모와 케이스 스터디

상태: **촬영 대본·케이스 스터디 초안, Android·iPhone 핵심 QA 및 로컬 Release 독립 실행 검증 완료 / 리허설·영상 촬영·일부 경계 QA 미완료**. 최신 구현 기준은 main `14a7977`이다. 양쪽 설치·증거 버전은 [Android preview](10-android-preview.md), [iOS preview](11-ios-preview.md)를 따른다. 아래 대본은 최신 실제 추천·재고 상태로 리허설 후 확정한다.

## 전달할 한 문장

“AI 초안을 사용자가 검수하고, 오늘 먹을 메뉴를 고른 뒤, 실제 남은 양까지 기록하는 식재료 관리 앱입니다.”

## 촬영 전 준비

- README의 로컬 실행 절차로 앱을 열고 동기화 대기·실패 표시가 해제됐는지 확인한다. 현재 사진 선택 흐름은 private 업로드와 서버 fixture 응답을 사용하므로 네트워크가 필요하다.
- 기존 재고를 지우지 않고 별도의 데모용 브라우저 프로필 또는 앱 설치 환경을 사용한다. 초기 시드도 있으므로 영수증 입고 전후 두부·애호박의 lot 수와 수량을 적는다. 같은 이름의 재고는 합쳐지지 않는다.
- 개인정보가 없는 데모 영수증 PNG/JPG 한 장을 준비한다. 사진 내용과 무관한 고정 fixture 결과임을 설명한다. 현재 진입점은 사진 라이브러리 선택이며, 앱 내 카메라 촬영을 시연한다고 표현하지 않는다.
- fixture는 6개 품목(확인됨 4개, 확인 필요 2개)이다. 참기름 수량을 `조금 남음`으로 수정하고 돼지고기를 제외하면 확정 버튼이 `5개 냉장고에 담기`가 된다.
- fixture의 초기 ISO 날짜는 2026년 8~11월로 고정돼 있다. 촬영일에 따라 추천 이유·순위가 바뀔 수 있으므로 실제 표시를 리허설에서 확인한다. 영수증 검수의 권장 섭취일은 `YYYY-MM-DD`로 편집하며 표시와 추천용 날짜가 함께 갱신된다. 비워 두면 미지정이고, 잘못된 날짜는 입고를 막는다. 포장 표기일은 별도로 유지한다. 날짜는 데모 데이터이며 섭취 안전 판단이 아니다.
- 조리 장면은 `애호박 두부덮밥`으로 준비한다. 실제 상위 3개에 있는지 확인하고, 없으면 현재 추천 중 부분·전량 차감을 함께 보여 줄 수 있는 메뉴로 대본을 조정한다. 결과 화면이나 추천 이유를 합성하지 않는다.
- 남은 음식 예시는 `남은 카레 · 1인분 · 냉장 · 내일까지`로 통일한다. 권장 시점은 사용자 입력이고, 보관 시작일과 구분해 보여 준다.

## 120초 촬영 대본

시간은 최종 편집본 기준이다. 입력·스크롤·업로드 대기는 줄일 수 있지만 `대기 구간 축약`을 표시하고, fixture 고지와 확정 전후 상태는 읽을 수 있게 남긴다. 브라우저로 촬영하면 시작 자막을 `웹 데모 · 모바일 뷰포트 · OCR fixture`로 표기한다.

| 구간 | 화면과 행동 | 내레이션 |
| --- | --- | --- |
| 00:00–00:10 | 홈과 오늘의 한 끼. 프로젝트명과 데모 환경 자막. | “남김없이는 1~2인 가구가 남은 재료로 오늘 먹을 한 끼를 결정하도록 돕는 앱입니다.” |

| 01:45–01:55 | 냉장고에서 두부 `반 모`와 전량 소비한 애호박 lot의 제외를 보여 준다. | “남긴 양은 재고에 이어지고, 다 쓴 재료는 활성 목록에서 빠집니다.” |

## 케이스 스터디 초안

### 문제와 가설

이 프로젝트는 1~2인 가구가 재고 목록을 꾸준히 정리하기 어렵다는 문제 가설에서 출발했다. 목표는 더 많은 재료를 등록하는 기능보다, 기록이 실제 메뉴 결정과 소비로 이어지는 흐름을 완성하는 것이다. 검수형 입고가 등록 부담을 줄이고, 이유가 있는 추천이 소비를 도울 것이라는 가설은 아직 사용자 조사로 검증하지 않았다.

### 범위를 줄인 결정

영수증 검수형 입고, 남은 음식 등록, 메뉴 선택 후 차감의 세 흐름에 집중했다. 현재 레시피는 데모용 5개이며, 자유형 LLM 레시피 생성 대신 재료 충족도·임박도·부족 재료·조리 시간으로 결정론적 추천을 구현했다. OCR provider는 연결하지 않고 fixture 결과와 제공자 미연결 고지를 유지했다. 바코드 DB·가족 공유·영양 분석은 범위에 넣지 않았다.

### 사용자의 확인을 데이터 경계로 만들기

검수 화면은 원문과 확인 필요 상태를 드러내고 이름·수량·보관 위치·권장 시점을 수정하거나 품목을 제외할 수 있게 했다. 확정 전에는 재고와 입고 원장을 변경하지 않는다. 확정 후에는 하나의 RPC로 lot와 원장을 같은 트랜잭션에 기록하며, 같은 batch를 재요청해도 중복 입고하지 않는다. 이 보장은 동일 batch에 대한 것으로, 같은 사진을 새로 업로드했을 때의 이미지 중복 탐지를 뜻하지 않는다.

### 소비를 다음 재고로 연결하기

조리 완료에서 자동 수량 계산 대신 실제 남은 양을 묻는다. `반 모` 같은 표현을 그대로 저장하고, 전량 소비한 lot는 활성 재고에서 제외한다. 조리 세션 선점과 차감 원장을 같은 트랜잭션으로 묶어 같은 세션의 재시도가 두 번 차감되지 않게 했다. 로컬 상태와 영속 outbox를 먼저 저장하고, 실패·대기 상태 및 재시도를 제공해 네트워크 실패 뒤에도 작업을 이어갈 수 있게 했다.

### 확인한 결과와 한계

| 주장 | 근거 | 해석의 한계 |
| --- | --- | --- |
| 검수·등록·부분/전량 차감 흐름이 동작한다 | 현재 컨텍스트의 375 × 812 웹 QA 기록과 [완료 시트 캡처](qa-artifacts/07-live-recipe-completion-sheet.png) | 캡처 한 장이 전체 플로우나 네이티브 동작을 증명하지는 않는다. |
| private 업로드부터 fixture 확정 입고까지 연결됐다 | 기존 새 익명 사용자 E2E: `ready / fixture → confirmed → already-confirmed`, public 원본 요청 HTTP 400 | 실제 OCR 정확도·실기기 사진 권한을 검증한 결과는 아니다. |
| 조리 차감은 같은 세션 재호출에 멱등하다 | 기존 Supabase E2E: 부분·전량 소비와 `confirmed → already-confirmed` 확인 | 모든 오류·경합 조건을 검증했다고 주장하지 않는다. |
| 등록·추천이 사용자 행동을 개선한다 | 아직 측정하지 않음 | 시간 절감률·등록 완료율·폐기 감소율을 성과로 제시하지 않는다. |

증거의 상세 상태는 [현재 컨텍스트](00-current-context.md), 구조와 실행 방법은 [README](../README.md), 실제 검수 동작은 [ReceiptEntrySheet](../src/features/receipts/ReceiptEntrySheet.tsx)를 따른다. 초기 기술 명세에 적힌 예정 라이브러리·레시피 수·OCR를 구현 완료로 인용하지 않는다.

후속 리뷰 수정에서 분석·검수 문구를 샘플 품목·fixture 초안으로 통일했다. 영상에서도 제공자 미연결 고지를 유지하고 실제 OCR 증거로 사용하지 않는다.

### 다음에 확인할 것

첫째, 완료된 핵심 기기 QA와 남은 경계 검증을 구분한다. iPhone·Galaxy의 핵심 입력·저장·재실행과 로컬 Release 독립 실행은 확인했고, Android도 최신 두 리뷰 수정의 갱신 설치·회귀를 마쳤다. HEIC/용량·긴 이름·접힘 전환 등 추가 범위는 [실기기 QA](09-device-qa.md) 및 각 preview 기록을 따른다.

둘째, 실제 타깃 사용자에게 영수증 수정·제외, 추천 이유 설명, 부분 소비를 요청한다. 도움 없이 완료했는지, 검수 시간이 얼마나 걸렸는지, fixture를 실제 OCR로 오해했는지, 권장일을 안전 보증으로 오해했는지를 관찰한다. 결과를 얻은 뒤에만 제품 효과와 개선 우선순위를 작성한다.
